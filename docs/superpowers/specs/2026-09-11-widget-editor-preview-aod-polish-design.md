# 小组件复活、编辑器预览与 AOD 界面修复设计

日期：2026-09-11

## 目标

本次修复覆盖四组相邻问题：

1. 恢复小组件页面原有的干净界面，移除顶部刷新按钮和常驻的“刷新失败，点击重试”提示。
2. 在不启动提供方可见 Activity 的前提下，进入小组件页面时主动请求系统拉起提供方进程并更新已绑定小组件，使真实 `RemoteViews` 能替换静态初始画面并恢复点击。
3. 把编辑器的预览设备和亮屏/息屏预览控制从顶部工具栏移动到“表盘设置”面板，并修复选中态、自定义尺寸和默认画布比例。
4. 让 AOD 与诊断界面使用 Flue 的颜色、控件和交互体系，同时把 WFTools 入口改到 Releases 页面。

## 不在范围内

- 不整体回滚 `8b1d7d3f`，不改动其中无关的多选编辑、渲染、商店和诊断能力。
- 不自动打开小组件提供方的 Activity，不尝试绕过 Android 的强行停止限制。
- 不改变 WatchMaker 表盘文件的设计坐标和导出格式；预览设备仅控制编辑器的外部预览视口。
- 不把单元测试或 Release 构建描述成第三方小组件的实机行为证明。

## 小组件更新与宿主生命周期

小组件页面不再维护用户可见的刷新失败状态，也不再提供手动刷新按钮。页面进入活跃状态时执行一次静默更新请求，短时间内的重复请求仍由节流器合并。

对每个仍然有效的已绑定 `appWidgetId`，更新协调器先通过 `AppWidgetManager.updateAppWidgetOptions` 让系统 AppWidget 服务向提供方发出宿主选项变化回调。该调用由系统按已绑定 ID 路由，可在提供方接收器不允许第三方直接广播时拉起其进程。随后发送定向的 `ACTION_APPWIDGET_UPDATE` 作为兼容路径，供依赖传统更新广播的提供方使用。任一路径的异常只写入带上下文的日志，不在页面上形成永久错误层。

`AppWidgetHost` 继续由应用级仓库持有，并在启动器 Activity 可见期间保持监听。页面预热可以提前创建 HostView，但只有页面实际进入活跃状态时才主动唤醒提供方，避免冷启动同时唤醒多个第三方应用。收到新的 `RemoteViews` 后沿用现有 HostView，无需重新绑定或替换 `appWidgetId`。

## 编辑器预览设置

顶部工具栏移除“预览设备”和亮屏/息屏两个文字按钮，保留返回、播放、画布全屏、面板全屏、撤销和重做。

“表盘设置”面板中，在“表盘形状”之后加入预览设置：

- “预览设备”使用与表盘形状一致的可选按钮样式，当前尺寸有明确选中态。
- 默认选中 WatchMaker 原生 `512×512`，不再按当前物理屏幕比例初始化。
- 预设包含当前设备与现有常用尺寸；选择后立即改变外部预览视口比例。
- “自定义尺寸”是可操作选项。点击后打开输入对话框，只有宽高均为正整数时才能保存；保存后该尺寸显示为当前选中值。
- “预览模式”提供“亮屏预览”和“息屏预览”互斥选项，当前模式有明确选中态。

外部预览区域继续受分屏高度限制，但其内部画布按所选视口宽高比双向等比缩放，不强制跟随设备屏幕比例。表盘渲染与命中测试仍使用 `512×512` WatchMaker 设计空间，因此预览视口变化不会修改图层坐标或导出内容。

## AOD 与诊断界面

AOD 保留现有 `AodPreferences` 作为唯一数据源，开关和滑块继续实时写入偏好；`AodController` 的监听器继续即时应用变化。界面层改用 Flue 的 Surface、主次文字色、`FlueSwitch`、`FlueSlider` 和按钮样式，并扩大整行点击区域。依赖总开关、充电启用或手势锁定的子项继续保持正确的启用状态。

诊断页同样停止依赖会在当前主题下产生黑字的默认 Material 内容色，标题、说明、状态、操作按钮和开关显式使用 Flue 主题角色。此次只修视觉接入，不改变诊断采集范围和功能。

## 错误处理

- 小组件更新请求允许单个提供方失败，不阻断其他提供方，也不显示永久重试 UI。
- 已失效或需要重新授权的 `appWidgetId` 继续走现有恢复/重新绑定卡片，不把绑定错误混同为刷新错误。
- 自定义预览尺寸输入非法时保留对话框并给出错误，不改变当前视口。
- AOD 悬浮窗权限与系统限制继续使用现有说明和授权入口，不承诺系统禁止的后台拉起行为。

## 测试与验证

先写失败测试，再实现：

1. 小组件更新计划覆盖有效 ID、系统选项回调、兼容广播、节流和单提供方失败隔离。
2. 编辑器预览状态覆盖默认 `512×512`、预设/自定义选中态、无效输入以及亮屏/息屏切换。
3. AOD 偏好测试覆盖开关、滑块写入后读取和控制器监听响应；诊断与 AOD 的源码级 UI 测试确认使用 Flue 控件和主题色。
4. 运行相关 JVM/Robolectric 测试、`git diff --check`，再在 Windows 原生环境运行 Release 构建与 APK 签名检查。

第三方提供方进程是否被系统拉起、真实内容是否到达以及 PendingIntent 点击是否恢复，最终仍需在装有对应小组件的物理设备上验证。
